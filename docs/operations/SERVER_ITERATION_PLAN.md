## 优先级一：开 GPU 之前完成所有本地准备

1. 在本地完成 kernel 设计、转换/接口修改、CPU/reference 测试与配置检查。
   Mac 不能代替 NVIDIA 数值/性能验证；本地通过只代表具备上机条件。
2. 将本次候选代码及文档提交并推送到 GitHub，确认远端分支 SHA。
   未推送成功、认证或网络尚未解决时不启动 GPU。服务器仍通过 Git 同步代码，
   不以复制工作目录替代 Git。
3. 固定要测试的候选版本、shape、dtype、groups_per_split、计时模式与验收阈值。
   提前准备 launcher、输出目录命名和失败停止规则。上机后不临时开展无边界搜索。
4. 如果必须重新编译较多候选，可在无 GPU 的 Linux x86_64 CUDA devel builder
   上预编译，目标 SM80、CUDA/PyTorch ABI 和部署路径必须一致；GPU 正确性仍在
   服务器运行。此项是后续可选优化，当前未建立或验证。

## 优先级二：固化软件环境，保留数据和缓存

分三层保存：

- **版本化镜像**：匹配的 CUDA devel/PyTorch、C++/ninja、已验证 Python 依赖、
  环境激活入口。镜像只包含稳定软件；不打入模型、结果、密钥或频繁修改的 kernel。
- **原网络卷**：原模型 snapshot、step400 payload、结果、Git checkout、wheel/pip
  缓存和按环境/SM 架构隔离的 extension cache。
- **Git 版本**：持续迭代的 kernel、runner、配置和文档，启动后同步到预先固定的 SHA。

本次基础镜像身份仍未知，before/after 都记录为 unresolved。不能直接把当前包清单
宣称为已验收镜像：下一次需要从 RunPod 模板详情确认镜像名/digest；若无法追溯，
另选明确且按 digest 固定的 CUDA devel 基础镜像，在 CPU builder 构建候选，再用
一次短 GPU 运行重新验收。新环境单独版本化，不冒充当前环境的精确复制。

镜像构建应在开 GPU 之前完成；记录发布后的 digest。镜像能消除大部分重复安装，
但还要测拉取和启动时间，不能保证总启动一定更快。当前 39 秒安装本身并不长。

**镜像未完成时的过渡方案**：继续用模板已有 torch/CUDA，预先准备已锁定依赖的
wheelhouse，启动后新建本机独立 venv 并从本地 wheel 安装，避免每次解析依赖与
网络下载；ninja 等构建工具优先放进稳定镜像。wheelhouse 按 Linux x86_64/Python
版本准备，不能拿 Mac wheel 或跨机器复制 venv。该流程本轮只规划，尚未实现。

缓存命名以后由 Python/torch/CUDA/nvcc/compiler ABI、SM 架构及编译 flags 决定，
不能每次使用日期创建全新目录。源码内容变化触发需要的重新编译；环境/架构变化
使用新 namespace，禁止把旧 .so 直接当作新版本验证结果。

## 优先级三：用一键入口替代多轮人工准备

拟增加两个明确入口，当前还未实现：

- `prepare_trial`（本地）：核对 GitHub SHA、生成冻结 trial 清单，确认镜像/依赖
  已准备，输出“可开 GPU”状态。源码未发布或关键配置缺失则失败。
- `resume_trial`（服务器）：检查挂载和磁盘、固定 SHA、激活镜像环境、选择缓存、
  校验实际用到的 payload、运行必要正确性检查，最后启动一个有界实验批次。
  使用 tmux/调度器持久执行，输出机器可读 status、阶段耗时、日志和退出码。

入口不把“SSH 通了”当作环境就绪，不在 entrypoint 自动拉取移动分支，不把失败
吞掉后继续计时。Git 认证使用短期/会话范围的机制；不把 token 写进镜像或日志。

每次开启时按变化范围验证：

| 变化 | 必须重做 | 可复用 |
|---|---|---|
| 环境、GPU 架构、源码和权重均未变 | 版本/设备/存储检查、轻量运行检查、该 trial 的真实形状数值 gate | 已验收依赖、兼容编译缓存 |
| kernel 源码改变 | 新编译、针对性 CUDA 测试、真实 shapes 数值 gate，之后才计时 | 相同环境、未变数据与依赖 |
| 环境或 GPU 架构改变 | 环境记录、编译和对应平台 CUDA gate | 内容无变化的原模型/权重文件 |
| 权重改变 | 新权重 hash/布局检查与数值 gate | 兼容 kernel 构建产物；旧计时仍绑定旧权重 |

不为节省时间放宽数值容差、减少正式计时重复次数或忽略稳定性失败。
首次环境可跑完整测试；普通重启不重复“首次冷编译 smoke + 再跑同一份全套测试”
这两个重复阶段，按变化范围执行一次适当测试集合。全套测试本身仅约 8 秒，
主要节省目标仍是冷编译和人工往返。

## 优先级四：一次开机测试一批有界候选

本地先准备少量有明确假设的 M=1 优化版本，保持冻结权重/数值语义不变。
例如输出 tile 宽度、split-K 粒度、激活与 scale 复用；这些是候选维度，当前
没有 profiler 证据证明哪一个是主因，不预先承诺加速幅度。

同一次开机内按清单执行：

1. 保留并同轮复测 v1 baseline，核对环境可比性。
2. 候选正确性 gate；失败则保存诊断，禁止为该格报告速度。
3. 对通过项运行冻结 eager/Graph timing，记录版本与每格稳定性。
4. 有明确需要时做一次有界 profiler capture，帮助下一轮本地修改。
5. 汇总小型结果并备份哈希，确认任务已结束后交还关机。

不逐次开机只跑一个五秒 trial。任何批次都要有候选数/时间上限，不能把批处理
变成无边界的自动调参或持续监控。block/full-model/vLLM 仍按独立阶段验收。

## 下次衡量是否真正变快

记录每一阶段的单调时钟耗时：镜像拉取/SSH 就绪（平台可提供时）、Git 同步、
环境激活、输入校验、编译、正确性、计时、备份。分别报告：

- 首次新环境的冷启动；
- 相同环境/源码的热启动；
- 相同环境、新 kernel 源码的启动。

暂定工程目标：相同环境和源码、缓存命中的情况下，**SSH 可用到启动 trial
争取控制在 30–60 秒内**。这是待测目标，不含平台调度和镜像拉取，也不是保证。
源码变化时允许额外编译时间，单列记录；不能把它算成缓存复用失败。
